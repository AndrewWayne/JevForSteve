# 技术路线决策：哪些已经清楚，哪些还没有

决策日期：2026-09-21。状态：**架构确定；摄像头适用性、眨眼适用性与 Jev 收益待实测。**

本项目交付的是可运行的工程原型与可执行的验证方案。目前没有患者试用结果、摄像头准确率结果、Windows 实机验收结果或 Jev 在线对照实验结果。界面演示、类型检查、模拟测试都不能替代这些证据。

## 1. 推荐路线

**Windows 单屏笔记本 → 本地摄像头特征/视线估计 → 个人屏幕映射 → 大目标预选 → 主动眨眼确认 → 本地文字或有限桌面操作。Jev 是可以关闭的语义辅助层。**

先解决“可靠表达一句自己的话”，再扩大到桌面操作。第一轮研发的核心产出不是更多按钮，而是回答：这个人、这个摄像头、这个姿势下，目标需要多大，误触会有多少。

| 决策 | 结论 | 把握与依据 |
| --- | --- | --- |
| 是否先校准 | 是；9 个训练位置 + 5 个独立验证位置 | 架构决定；点数、采样时长是待调参数 |
| 校准什么 | 屏幕坐标；不校准实体 Q/P/A/L/Z/M | 实体键盘是另一个平面，低头还可能遮挡眼睛；不符合第一版表达闭环 |
| 普通摄像头能否替代专用仪器 | 能研究、能做个体化原型，不能预先保证替代 | 文献可行性不等于特定设备和 ALS 用户可用性 |
| 默认目标布局 | 摄像头模式优先分组大键；密集 QWERTY 要通过额外任务验证 | 目标尺寸必须由误差决定，而不是视觉稿决定 |
| 点击方式 | 个人化主动眨眼；闭眼前冻结预选目标，睁眼后提交 | 用户选择；自然/主动眨眼重叠时不能勉强启用 |
| Jev 看什么 | 1–4 个本地候选、短上下文、明确任务；文本 JSON | 官方接口只接收文本，不接收视频/图像 [S1] |
| Jev 决定什么 | 有语义证据时建议预选词/控件；必要时弃权 | 不能可靠推断隐藏意图，不能批准点击 |
| Jev 不决定什么 | 视线坐标、眨眼检测、数值阈值、是否执行、输入权限 | 这些交给可检验的本地代码 |
| 桌面接入 | Windows UI Automation 语义目标优先，有限 SendInput | 初版读出按钮到面板里；不是全屏任意点鼠标 |
| 中文 | 初版常用短语；下一阶段接本地拼音/Rime 候选引擎 | Jev 不是生成式拼音引擎；官方提示 CJK 表现弱于英语 [S1] |

## 2. 算法选型：两条路线并测，而不是提前押注

| 路线 | 优点 | 局限 | 项目安排 |
| --- | --- | --- | --- |
| A：MediaPipe 面部/虹膜特征 + 个人岭回归 | CPU 本地可运行、少依赖、便于观察故障；可共享眼睑特征 | MediaPipe 不直接提供视线；头动、反光、眼部像素不足会破坏映射 | **已实现基线**；只作为可替换的实验起点 |
| B：预训练外观视线网络 + 个人屏幕映射 | 使用眼图像/头姿，而不只靠几个坐标；可能更适合变化姿势 | 方向不等于屏幕点；需裁剪、归一化、摄像机/屏幕关系及许可证审查 | **优先比较 OpenVINO gaze-estimation-adas-0002；L2CS 作为第二候选**，尚未集成 |
| C：GazeFollower | 有校准、采集与完整研究流程 | 仓库标明 CC BY-NC-SA；更大权重另有限制；眨眼等仍列为待实现 | 文献/离线研究比较，不作为本 MIT 原型默认依赖 |
| D：WebGazer | 浏览器方案成熟、容易复现研究 | GPLv3；官网说明 2026-02-24 起不保证继续更新；常见点击校准不适合本目标用户 | 对照思路，不复制代码 |
| E：专用红外眼动仪 | 专门的照明与光学系统、完整设备校准 | 需要额外设备，SDK/成本/可获得性各异 | 普通摄像头不达标时的产品输入适配器 |

**选择 B 的具体规则**：相同设备、相同校准时间、相同受试者分段测试。只有 B 在留出位置误差、20 分钟漂移、目标命中、有效帧率和疲劳任务中整体更好，才取代 A。不能用不同论文的角度 MAE、手机厘米误差和本项目屏幕像素误差直接排序。

当前 A 的特征是左右虹膜相对眼角位置、眼睛方向与脸部位置/尺度代理量。它不是精确三维头姿，不是训练完成的医疗用途视线模型。B 是候选路线，不是仓库已经具备的能力。

## 3. 为什么“大键”不是可有可无的 UI 细节

举例而非性能测量：屏幕宽 344 mm、1920 px，眼睛距离 600 mm。1° 对应约 `600 × tan(1°) = 10.5 mm ≈ 58 px`；2° 约 117 px。70 px 宽的小按键在这种误差下会相互混淆。Jev 不能凭语义把物理分辨率问题彻底消掉，尤其是姓名、密码、否定词和新词。

所以产品顺序应是：大目标 → 两级字母组 → 词候选减少操作 → 条件允许再开密集键盘。悬浮条可以小，但用户正在选择的目标不能为了“简洁”而小。

## 4. 第一版交互闭环

照护者协助开摄像头、找舒适姿势 → 视线校准和验证 → 自然/主动眨眼分离检查 → 看向字母组 → 预选高亮稳定 → 有意慢眨眼 → 睁眼后选择 → 组成文字 → 朗读。

桌面操作沿用同一个选择机制：先读取当前窗口的语义按钮，面板中显示大目标；选择后再显示确认。原生层执行前复查窗口、目标位置、有效时间。不能把“模型认为应当发送”当作用户点击了发送。

眼睛丢失、无目标、校准不合格、过期模型结果均不产生输入。“看键盘/看屏幕/什么都没看”的三分类不是第一版的必要前提：只接受校准域内、有效追踪下的可见目标命中，其余情况放弃选择。可靠的屏幕外注视检测仍需要负样本验证，不能只靠把预测点裁剪进屏幕。

## 5. 三个必须补齐的实验

1. **设备与算法适用性**：A/B 配对比较，至少覆盖两个摄像头、戴镜/不戴镜、两种光线、重新坐姿；训练点与验证点严格分离。先健康志愿者工程排障，随后由合适的辅助沟通专业人员协助个体试用。
2. **眨眼选择可用性**：记录自然阅读、主动确认、持续闭眼、丢帧、疲劳后的混淆。不能假定所有 ALS 用户一直能主动眨眼。若不可分，转驻留/外接开关方案；当前版本这两个后备尚未实现。
3. **Jev 增益**：同一组匿名候选事件，对比几何规则、局部词频、局部词频 + Jev。主要看错误提交和修正后速度，不能只看分类准确率；中文单列，不混在英语平均分里。

工程门槛、数据格式、退出条件见 [校准与评估](05-calibration-and-evaluation.md)。它们是提出的验收标准，不是已达到的数据。

## 6. 路线何时才能称为“验证清楚”

- 摄像头路线：真实任务证明目标尺寸与错误率可接受；能说明在哪些条件失败。
- 眨眼路线：用户本人能稳定区分自然和主动动作，持续使用后依然成立。
- Jev 路线：对照实验显示有增益；无增益时仍保留完整本地输入。
- 桌面路线：Windows 实机证明焦点、缩放、过期目标、受保护窗口均按设计处理。

现在是**可以开工且知道如何证伪的路线**，不是已经证明适合患者日常独立使用的产品。
